## 2. The important part: new defects it found

These are not in the original report. They affect whether H2 can be called a
pass, so they need triage before the study is treated as settled.

1. **The implemented H2 gate omits preregistered clauses.** `added_info_pass`
   checks only Jacobian-vs-logit median Jaccard and the Wilcoxon p-value. The
   proposal also required separation from the output and prompt-only baselines
   beyond rerun noise. Those clauses were never evaluated.
2. **Declared inference seed `[1]` was never executed.** The notebook declares
   seeds `[0,1]` but only sets seed 0.
3. **Specificity used one random-vector seed.** Three seeds `[0,1,2]` were
   computed; the specificity decision used seed 0 only.
4. **The D-margin rule couples non-redundancy and specificity** and may have
   insufficient headroom.
5. **The report does not expose all statistics needed to independently certify
   the gates**, and the primary artifacts were never transferred.

## 3. Runtime work done this session (two bugs, both fixed)

### Bug A — 400 "requires a newer version of Codex" (self-inflicted, fixed)

Starting the stack with `--workdir /Volumes/Asylum/archimedes-wt-jspace` put that
worktree's own `EvoScientist/` package ahead of the editable install on
`sys.path`, because `langgraph_dev/manager.py:739` hardcodes `cwd=workspace_dir`.
The server therefore ran docs-branch code, which hardcodes
`_CODEX_CLIENT_VERSION = "0.142.5"`. Probe matrix: `gpt-5.6-sol` is rejected at
0.142.5, accepted at 0.144.1 and 0.145.0.

**Resolution at the time:** the workdir was the study-document subdirectory of
`/Volumes/Asylum/archimedes-wt-jspace`, which contained no `EvoScientist/`
package to shadow with. The repository directory was renamed `j-space-lab` on
2026-07-30. Verified then: imports resolved to
`/Volumes/Asylum/archimedes/EvoScientist`, client version 0.145.0.

**Keep this in mind:** never point `--workdir` at a directory that is itself a
checkout of this repo. cwd cannot be separated from workdir via the CLI.

### Bug B — silent empty answers on the Codex route (pre-existing, fixed)

ccproxy's `StreamingBufferService` drops the body when assembling a
**non-streaming** Responses reply at agent scale: the client receives
`status: completed` with an empty `output` array, which LangChain correctly
parses into `AIMessage(content=[])`. No error is raised anywhere. This is the
"empty-message bug" open since 2026-07-24.

Decisive evidence: a byte-identical captured 37-tool payload replayed through
ccproxy twice with only `stream` toggled — `false` gives `output_items: 0`,
`true` gives full SSE with the real text. Forcing Chat Completions is not an
escape; the same missing `output` surfaces there as a 502 "Failed to convert
provider response using format chain".

`models.py:547` did `kwargs.pop("streaming", None)` under a comment stating
streaming must stay ON. `pop` only removes an explicit value, so LangChain's
`streaming=False` default applied and requests went out `stream: false`.

**Shipped fix:** `EvoScientist/middleware/ccproxy_stream.py`, registered in
`EvoScientist.py` immediately *inside* the tool selector. It sets
`model_settings={"stream": True}` per call, for the ccproxy Codex Responses model
only. Per-call rather than per-instance is load-bearing: setting
`ChatOpenAI.streaming = True` would also reach the tool selector's
structured-output copy, which sets `disable_streaming=True` — that suppresses
LangChain's dispatch but `langchain_openai/chat_models/base.py:1374` still
serializes `stream: true` onto the wire, and the Responses branch of `_generate`
never pops it, so a `Stream` would be handed to code expecting a completed
`Response`.

Tests: `tests/test_ccproxy_stream_middleware.py`, 16 tests including
payload-level guards. Full suite on `fix/ccproxy-codex-streaming` standing alone:
**3052 passed, 12 skipped** (3036 on `main` plus these 16). The 3058 figure is the
combined total with #6 also applied.

**Not repaired:** the actual defect is server-side in ccproxy's non-streaming
assembly. It cannot be patched from EvoScientist — ccproxy runs as a separate OS
process (`ccproxy_manager.py:7`, "invoked via subprocess, not Python imports"),
so the client-side monkey-patches in `llm/patches.py` never reach it. Note that
`patches.py:139-157` is dead code for this reason and only handles
`output is None` anyway, not the observed `output == []`.
